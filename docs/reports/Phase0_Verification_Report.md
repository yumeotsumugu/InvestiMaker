## 3. §13 各項目

### 3.1 マスターキャンバス — 検証済み（PC）／人間の判断待ち（スマホ実機・画質）

**試したこと**：同じ仮素材を 1200×1800 / 1600×2400 / 2000×3000 で生成し、全 18 Part を装備した状態（描画 27 Layer）で計測した。

**得られた事実**（ヘッドレス Chrome、デスクトップ PC、3 回の中央値）：

| 項目 | 1200×1800 | 1600×2400 | 2000×3000 |
|---|---|---|---|
| 初回合成（画像の取得・復号＋色変更＋描画） | 81 ms | 120 ms | 158 ms |
| 何も変えずに再合成 | 10 ms | 15 ms | 24 ms |
| 色変更：肌（7 枚） | 17 ms | 30 ms | 46 ms |
| 色変更：コート main（4 枚） | 21 ms | 36 ms | 56 ms |
| 色変更：髪（3 枚） | 12 ms | 22 ms | 32 ms |
| 全 Layer を色変更し直す | 45 ms | 77 ms | 114 ms |
| PNG 書き出し（`toBlob`） | 9 ms | 13 ms | 15 ms |
| メモリ見積もり（読み込んだ画像＋色変更キャッシュ＋キャンバス） | 31 MB | 55 MB | 85 MB |
| 同じ 52 枚がキャンバス全面サイズだった場合 | 429 MB | 762 MB | 1,190 MB |

CPU を 4 倍低速にするエミュレーション（実機の代わりにはならない目安）：

| 項目 | 1200×1800 | 1600×2400 | 2000×3000 |
|---|---|---|---|
| 初回合成 | 358 ms | 520 ms | 725 ms |
| 色変更：コート main | 73 ms | 126 ms | 194 ms |
| 全 Layer を色変更し直す | 177 ms | 286 ms | 452 ms |

- 時間もメモリも、ほぼ画素数に比例する（1600 は 1200 の約 1.8 倍、2000 は約 2.8 倍）。
- メモリ見積もりの内訳（1600×2400）：読み込んだ画像 6.97 Mpx、色変更キャッシュ 3.49 Mpx、キャンバス 3.84 Mpx。**色変更方式は元画像・Mask・変更後の 3 枚を持つ**ので、Mask 付き Asset は画素数の 3 倍のメモリを使う。
- トリミングの効果は約 14 倍。仕様書 §4.2 の SHOULD は妥当で、公式素材では事実上必須にしてよい。
- メモリ見積もりは「画素数 × 4 バイト」の計算値で、ブラウザの実使用量ではない。

**推奨**：1600×2400 を維持。PC では色変更が 1 フレーム〜数フレームで終わり、カラーピッカーのドラッグに追従できる。2000×3000 にする積極的な理由は今回見つからなかった。

**人間の判断が必要な点**：
- **スマホ実機での計測が未実施。** 検証ページは `npm run dev -- --host` で LAN に出せば実機で開ける。`?set=bench/2000x3000&bench=1` を付けると自動で計測し、結果が画面下に出る。見るべき値は初回合成・色変更・「メモリ見積もり」。
- **出力画質**は仮素材（図形）では判断できない。実際の画風で 1 Part 描いて、1600×2400 の書き出しをココフォリア等に置いて確認する必要がある。
- 仮素材は Layer 数も面積も実素材より小さい。実素材では髪・衣装の面積が増えるので、上の値は下限と見るべき。

### 3.2 `tint` の基準下地 — 検証済み／人間の判断待ち（発色の好み）

**試したこと**：衣装（コート・ボトムス・帽子・靴）、肌、髪に明色・暗色・高彩度色・肌色を指定して並べた。下地は影 64・基準 128・ハイライト 198。

| 画像 | 内容（左上から右へ） |
|---|---|
| [images/tint_clothes.png](images/tint_clothes.png) | 既定 `#3A3F4B` / 明色 `#F4F4F0` / 純白 `#FFFFFF` / 暗色 `#101014` ／ 純黒 `#000000` / 赤 `#E60033` / 黄 `#FFE000` / 青 `#0050FF` |
| [images/tint_clothes_multiply.png](images/tint_clothes_multiply.png) | 同じ指定を `multiply` で合成（素材は `tint` 用のグレー下地のまま） |
| [images/tint_skin.png](images/tint_skin.png) | 肌 `#FFE8D6` / `#F2D3BD` / `#D9A066` / `#A0673C` / `#5C3A21` / `#2E1A0E` |
| [images/tint_hair.png](images/tint_hair.png) | 髪 `#0A0A0A` / `#5A3E2B` / `#E8D080` / `#F8F8F8` / `#FF70A0` / `#2040C0` |

**得られた事実**（全色の数値は [data/tint-samples.json](data/tint-samples.json)。線画色は `#2A2630`）：

| 指定色 | 影（下地 64） | 基準（下地 128） | ハイライト（下地 198） |
|---|---|---|---|
| 純白 `#FFFFFF` | `#808080` | `#FFFFFF` | `#FFFFFF` |
| 明色 `#F4F4F0` | `#7A7A78` | `#F4F4F0` | `#FAFAF8` |
| 既定 `#3A3F4B` | `#1D2026` | `#3A3F4B` | `#A7A9AE` |
| 暗色 `#101014` | `#08080A` | `#101014` | `#949496` |
| 純黒 `#000000` | `#000000` | `#000000` | `#8D8D8D` |
| 赤 `#E60033` | `#73001A` | `#E60033` | `#F48DA3` |
| 肌 `#F2D3BD` | `#796A5F` | `#F2D3BD` | `#F9EBE1` |
| 濃い肌 `#5C3A21` | `#2E1D11` | `#5C3A21` | `#B6A79B` |

- **基準 128 では、どの色も指定色そのものになる**（単体テストで固定）。ただし仕様書の式どおりだと 1 段ずれる（P1）。
- **明色は白飛びする**：純白ではハイライトが完全に消え、`#F4F4F0` でも差は 6 段。一方で影は残る（純白の影は `#808080`）。白い服は「影だけで立体を出す」ことになる。
- **暗色は影が潰れる**：`#101014` の影は `#08080A` で、基準との差は 8 段。純黒では影が完全に消える。
- **暗色ではハイライトが強すぎる**：黒い服のハイライトが `#8D8D8D` の明るいグレーになる（画像では金属のような光沢に見える）。ハイライトは「指定色から白へ」の補間なので、指定色が暗いほど変化量が大きい。
- **暗色では線画が塗りに埋もれる**：線画色 `#2A2630` より暗い色を指定すると、線が塗りより明るくなる。既定のコート色 `#3A3F4B` でも影の部分は線との明度差が 0.03 しかない。肌 `#2E1A0E` では顔の輪郭と鼻・口の線がほぼ見えない。
- 高彩度色は、影が同じ色相のまま暗くなり、ハイライトは白へ寄って彩度が落ちる。破綻はない。
- `multiply` は、グレー下地の素材に使うと全体が約半分の明るさになる（`#FFFFFF` を指定しても `#808080`）。`tint` 用と `multiply` 用の素材は下地を描き分ける必要があり、検証ページの切り替えは「同じ素材では代用できない」ことの確認になった。

**推奨**：
- 50% グレー基準を維持する。「指定した色がそのまま出る」ことが色選びの分かりやすさに直結し、影もハイライトも 1 枚で表現できる。
- 式の境界は 0.5 ではなく 128/255 とする（P1）。
- 作画ガイドラインとして「ハイライトは控えめに描く（下地 160 程度まで）」「影は 64 より浅めにする」を検討する。暗色でのハイライトの強さと、明色での影の重さの両方を和らげる。
- 暗色で線が埋もれる問題は規格では解決しない。UI 側で色の下限を設けるか、線画色を Part ごとに変えられるようにするか、許容するかの判断になる。

**人間の判断が必要な点**：
- 上の 4 枚を見て、**黒い服のハイライト**と**白い服の影**が許容できるか。
- 濃い肌色・黒髪・黒い服で**線が見えなくなること**を許容するか。
- 実際の画風の塗り（影・ハイライトの面積と濃さ）で同じ比較をやり直す必要がある。仮素材のグラデーションは人工的で、発色の最終判断には使えない。

### 3.3 Mask の A チャンネル — 検証済み（確定可）

**試したこと**：RGB に 0〜255 の全値、行ごとに異なる A を入れた PNG（`assets/probe/mask_alpha_probe.png`）を、Mask と同じ経路（`createImageBitmap` に `premultiplyAlpha: 'none'` を指定 → `drawImage` → `getImageData`）で読み、元の値と比べた。

**得られた事実**（Chrome 154）：

| A の値 | 読み戻した A | RGB の最大誤差 | RGB が元の値と一致した画素 | 読み戻した R の値の種類（元は 256） |
|---|---|---|---|---|
| 0 | 0 | 255 | 0% | 1 |
| 1 | 1 | 127 | 0% | 2 |
| 8 | 8 | 16 | 0% | 9 |
| 32 | 32 | 4 | 0% | 33 |
| 64 | 64 | 2 | 0% | 65 |
| 128 | 128 | 1 | 22% | 129 |
| 192 | 192 | 1 | 55% | 193 |
| 254 | 254 | 1 | 99% | 255 |
| 255 | 255 | 0 | 100% | 256 |

- A そのものは正確に読める。壊れるのは RGB で、**階調が A+1 段に減る**（内部でアルファを乗算して 8bit で持つため）。A = 0 では RGB が完全に失われる。
- つまり A を 4 つ目のスロットに使うと、その適用率が低い画素で他の 3 スロットの適用率が壊れる。仕様書 §4.3 の記述は実測と一致する。
- 同じ劣化は **Asset 側の半透明画素にも起きている**。ブラウザの書き出しと、ブラウザを使わない合成を比べると、不透明な画素の差は最大 2 段、半透明の縁の画素では最大 48 段（差のある画素は全体の 0.4%）。アルファを乗算した値で比べれば、半透明の画素も含めて差は最大 2 段に収まる。見た目には分からないが、実装間のビット一致はできない（P13）。

**推奨**：A チャンネル不使用で確定する。4 スロット以上は `masks` 配列で持つ（実装済み、単体テストあり）。

**未検証**：WebGL での読み出し（今回は使わない方針のため）。PNG を自前で復号すれば A を使えるが、復号コストと実装の複雑さが増えるので、3 スロットで足りないことが分かってから検討すればよい。

### 3.4 標準描画順 — 検証済み／人間の判断待ち

**試したこと**：全 Part を装備した状態と、比較用の切り替え 2 種。

| 画像 | 内容 |
|---|---|
| [images/default_1600x2400.png](images/default_1600x2400.png) | 全 Part を標準順で合成 |
| [images/order_eyebrows.png](images/order_eyebrows.png) | 左：眉が前髪の後ろ（RC1 の標準 `face.eyebrows`）／右：眉が前髪の前（草案 0.2 の標準。RC1 では `face.eyebrows.over`）。見分けやすいよう眉を黒にしてある |
| [images/order_shoes.png](images/order_shoes.png) | 左：`outfit.shoes`（靴が裾の下）／右：`outfit.shoes.over`（靴が裾の上） |
| [images/order_glasses.png](images/order_glasses.png) | 左：メガネなし／右：メガネあり（前髪の前） |
| [images/order_blush.png](images/order_blush.png) | 左：赤面なし／右：`overlay.face`（輪郭の上、口・鼻・目の下） |
| [images/pose_pocket.png](images/pose_pocket.png) | 左から：down＋コート／pocket（コートは非対応で消える）／down／pocket |

**得られた事実**：
- 仮素材 18 Part の範囲では、重なりが破綻する組み合わせは見つからなかった。
- **眉と前髪**：草案 0.2 の標準順（画像の右）では、眉が前髪の上に不透明で描かれる。髪と同じ色（共有カラー `hair.base`）だと目立たないが、色が違うと前髪を貫通して見える。「眉が髪から透けて見える」表現にしたい場合、眉の Asset 自体を半透明に描くか、前髪に隠れた部分だけ薄くする仕組みが要る。逆順（画像の左）は眉が前髪に隠れ、前髪の長い髪型では表情が読みにくくなる。
- **靴と裾**：どちらも成立する。標準の `outfit.shoes` はスニーカーや革靴、`outfit.shoes.over` はブーツ向き。Slot を 2 つ持つ現在の設計で対応できる。靴の Part が Layer を両方の Slot に分けて持つこともできる。
- **メガネ**：前髪の前に出る。前髪の房がレンズの下に見える。
- **赤面**：`overlay.face` は目・口の下に入るので、目に被らない。
- **腕グループ**：`down` を背面（G2）、`pocket` を前面（G6）とした（実装側の判断、P6）。背面の腕は袖ごと胴体と身頃の後ろに回り、肩の継ぎ目が身頃で隠れる。前面の腕は頭部より手前に出るので、腕を顔の前に上げるポーズにも使える。
- **pocket の手**：素体の右手は `optional: true` で `down` の画像だけを持たせた。`pocket` では「省略」になり、素体は対応のまま。`optional` の用途として適切だった。

**推奨**：§6.1 の順序は変更不要。眉の扱いだけ判断が要る。

**人間の判断が必要な点**：
- [images/order_eyebrows.png](images/order_eyebrows.png) の左右どちらを標準にするか。眉を前髪の前に置くなら、眉を半透明にする作画ルールを決める。→ **RC1 で「前髪の後ろ」を標準に決定**（§7）。
- [images/order_shoes.png](images/order_shoes.png) で、公式の靴をどちらの Slot に置くかの方針。
- 実際の画風では、横髪と耳、襟と首、後ろ身頃と後髪で問題が出やすい。仮素材には横髪・襟・首回りの Part がなく、**そこは未検証**。

### 3.5 表情の標準状態名 — 所見のみ（画風決定後に再検討）

- 目 6・眉 5・口 6 の状態を持つ仮素材を作り、`state` で解決できることを確認した（[images/expressions.png](images/expressions.png)、左から normal / smile / angry / sad / surprised / fear）。
- 標準表情 6 種のうち、仕様書が状態の組を示しているのは `smile` だけ。残りは実装側で仮に決めた（`src/core/context.ts` の `STANDARD_EXPRESSIONS`、P8）。
- その仮の割り当てでは、目の `closed` と口の `smile` がどの標準表情にも使われない。状態名が多いのか、標準表情が足りないのかは、画風と表情の方針が決まってから見直す。
- 状態名の過不足そのものは**未検証**。

### 3.6 `fitDimensions` — 所見のみ

- `chest: small / medium / large` を素体に宣言し、素体とシャツに `large` 専用画像を持たせた。`large` では専用画像を持つ Layer だけが切り替わり、コートは fit 非依存の画像に落ちた（[images/fit_chest.png](images/fit_chest.png)、左から 素体 medium / large、シャツ medium / large、コート medium / large）。
- この仮素材では、fit 非依存のコートが `large` のシャツを覆い、はみ出しは起きなかった。ただしこれは図形の寸法がたまたま収まっただけで、実素材では「fit 非依存と宣言した外衣が、fit 違いの内側を覆えるか」が素材ごとの課題になる。
- 画像数：`chest` の値が 3 つでも、専用画像は `large` の 1 枚で済んだ（`small` と `medium` は共通画像）。次元を増やした場合の掛け算は**未検証**。
- 素体の fit の値を、Part 側の `when.fit` が参照できる値として検証する仕組みがない（素体が宣言していない次元や値を書いてもエラーにならない）。P5 を参照。

### 3.7 パッケージ上限 — 未検証

- 仮素材は 18 Part・120 ファイルで合計 570 KB、1 Part あたり最大 16 ファイル（素体：7 Asset × 画像と Mask ＋ manifest ＋ プレビュー）。図形なので圧縮が効きすぎており、実素材のサイズ感の材料にならない。
- ファイル数の見積もりだけ示す：目の Part が 5 VIEW × 6 状態を持つと、画像と Mask で 60 ファイル。袖が 5 VIEW × 腕の状態 4 つ × fit 2 つだと 1 Layer で 80 ファイル。500 ファイルの上限は、VIEW とポーズが増えた衣装 1 着で届きうる。
- 実素材 1 セットができてから再検討する。

### 3.8 帽子と髪の干渉 — 所見のみ／人間の判断待ち

- 帽子に `hides: ["hair.extra"]` を付け、頭頂の追加髪（アホ毛）が消えることを確認した（[images/order_hat_hair.png](images/order_hat_hair.png)、左から 帽子なし／帽子あり／帽子ありで `hides` を外した場合）。
- `hides` がないと、追加髪の先が帽子の上に突き出る（右）。`hides` で解決できている。
- **`hides` で扱えないもの**：後髪は帽子より後ろ（`hair.back` は `outfit.head.back` より手前、`outfit.head` より奥）にあり、帽子のクラウンより外側にある部分はそのまま見える。仮素材では自然に見えるが、ボリュームのある髪型では帽子の上や横から髪がはみ出す。`hides: ["hair.back"]` にすると後髪が丸ごと消えてしまう。
- 前髪は `outfit.head` より奥なので、帽子に覆われる部分は隠れ、つばの下の房は残る。これは意図どおり。

**人間の判断が必要な点**：切り抜きの仕組み（帽子が「髪を隠す領域」の Mask を持つ等）が要るかどうかは、実際の髪型と帽子を数種類描いてみないと決められない。v1 は `hides` のみとし、「帽子用の髪 Asset を `when` で切り替える」案（髪側に `when.attach` や新しいキーを足す）と比較するのがよい。今回は実装していない。

### 3.9 ITEM の装着仕様 — 未検証

今回の対象外。気づいた点だけ記す。
- `LayerContext.attach` は型だけ用意し、常に未指定とした。`when.attach` を書いた Asset は一致しない。
- 腕グループには `item.hand.<side>` があり、`arm.<side>.hand`（手）と `arm.<side>.hand.front`（指）の間に入る。物を握る表現はこの 3 Slot で作れる見込みだが、試していない。

## 4. 実装して分かったこと（§13 以外）

- **Asset 解決（§6.5）は仕様書の手順だけで実装できた。** 具体度の比較と重複の禁止で、実行時の同点は起きない。Asset の並び順を逆にしても結果が変わらないことをテストで確認した。
- **「非対応」の伝わり方**：検証ページでは、コートの 4 Layer のうち未解決の 1 行を赤、残り 3 行を「描画しない」で表示した。どの画像を足せば対応になるかが一覧から読み取れる。製品 UI でも同じ情報を出せる。
- **共有カラー**：リンク解除の瞬間に見た目が変わらないよう、その時点の共有色を個別色の初期値にした。仕様書には書かれていないが、UI 挙動の文書に入れる価値がある。
- **色変更のキャッシュ**：Asset 単位で「スロットの色とモード」をキーにした。色を 1 つ変えると、そのスロットを使う Asset だけが再計算される。
- **手を付けなかったもの**（指示書 §7）：保存 / 読込、ZIP、SVG、正面以外の VIEW、ITEM、COMPOSITION / PORTRAIT、VARIANT、Undo / Redo、Advanced Mode、JSON Schema。`mirrorable` の反転と Transform は型だけ。
- **次の段階への提案**（実装していない）：
  - `tests/conformance/fixtures/` を `.impart` の適合性テスト素材に育てる（今は Layer の断片と期待結果だけ）。
  - manifest の JSON Schema は、`src/core/validate.ts` の検査項目とエラーコードを基に起こせる。ただし `when` の重複検出は Schema では書けないので、検証器との二本立てになる。
  - 色変更を Web Worker か WebGL に移すかは、スマホ実機の計測値を見てから決める。

### 7.2 変更提案の採否

| 提案 | 本書の提案 | 決定 |
|---|---|---|

### 7.4 Phase 1 へ持ち越すもの

- スマホ実機での性能試験（検証ページの `?bench=1` がそのまま使える）。
- 実際の画風での発色・画質・頭部まわりの重なりの確認と、Authoring Guide の作成。

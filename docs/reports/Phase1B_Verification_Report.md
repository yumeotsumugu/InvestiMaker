## 2. 最小 UI の操作フロー

画面は 1 つで、左に Parts、中央に Preview と状態表示、右に State・共有色・選択中の Part の Colors と Transform がある（[images/app_edited.png](images/app_edited.png)）。

| 操作 | 画面 | 呼ばれる処理 |
| --- | --- | --- |
| 新規作成 | ヘッダーの「新規作成」 | `newSession`：`createCharacter` と `addInstance`（素体と最初の 12 Part） |
| Part 選択 | Parts の「装備」「追加」「付ける」 | `choosePart`：1 Part だけの category では同じ category の装備中の Part を `setEquipped(false)` で外してから `equipPart` |
| 外す / 削除 | Parts の「外す」「削除」 | `setEquipped(false)` / `removeInstance` |
| 色 | 共有色、Colors のカラーピッカーと「共有色」のチェック | `setSharedColor`、`setInstanceColor`、`unlinkColor`、`relinkColor` |
| State | VIEW・3 領域のポーズ・表情・目・眉・口・fit の選択 | `setView`、`setPose`、`setExpression`、`setFit` |
| Transform | 適用範囲と 5 つの数値 | `setTransform`、`setTransformOverride` |
| JSON 保存 | 「JSON 保存」 | `stringifyCharacter`（`requirements` を作り直す） |
| JSON 読込 | 「JSON 読込」でファイルを選ぶ | `loadCharacterText`：`parseCharacter` → 成功なら置き換え、INVALID なら現在のまま |
| PNG 出力 | 「PNG 出力」 | Preview のキャンバス（1600×2400、透過）をそのまま書き出す |

どの操作も「DOM のイベント → Character の操作 → 評価（`evaluateCharacter`）→ 描画計画（`planCharacter`）→ 描画」の一方向で動く。画面は Character から毎回作り直しており、DOM 側には Character の写しを持っていない。

選択肢は実装が知っている定義から作っている：VIEW は `VIEWS`、ポーズは Pose Definition、表情は標準表情と標準状態名、fit は素体の `fitDimensions`。読み込んだ Character が選択肢にない値（未知のポーズなど）を持っていた場合は、「（未知）」と付けてそのまま表示し、消さない。

## 4. Transform の検証結果

### 4.1 描画への反映

- 適用順は Asset 仕様 §9 のとおり「`pivot` を中心に拡大縮小 → 回転（度、時計回り）→ 平行移動」。行列として 1 つにまとめ、ブラウザでは Canvas の `setTransform`、ブラウザを使わない合成では逆変換と双線形補間で適用する。
- 行列の単体テスト：平行移動、`pivot` を中心にした拡大縮小、`pivot` 省略時のキャンバス中央、90 度の時計回り、適用順。
- 描画のテスト：メガネに `{ x: 12, y: -30 }` を与えると、メガネの画素の外接矩形がちょうど (12, −30) だけ動く。拡大すると幅が広がり、回転すると画像が変わる。
- 整数の平行移動は、置く位置をずらした場合と画素単位で同じ結果になる（補間を通さない）。

### 4.2 気づいた点

- **ブラウザとの一致は保証できない。** 拡大・回転・小数の移動では、Canvas とソフトウェア合成で補間の方法が違うため、画素単位では一致しない。Asset 仕様 §13.2 の許容差（±2）は補正のない描画について実測したもので、補正のある Layer には当てはまらない（§8 の変更案 4）。保存 → 読込の一致は、同じ描画経路どうしで確かめている。
- **`pivot` の既定値が使いにくい。** 省略時はキャンバス中央（800, 1200）なので、帽子やメガネを拡大・回転すると、頭の位置ではなく腰のあたりを軸に動く。Phase 1-B の UI は `pivot` を編集できないため、拡大と回転は事実上「位置もずれる」操作になっている（§7 の 2）。
- **Part 既定の補正との合成方法が、Asset 仕様では決まっていない。** 「差分として合成」とだけあるので、位置と回転は加算、拡大縮小は乗算、`pivot` は Instance 側を優先、と解釈した（§8 の変更案 3）。仮素材に Part 既定の補正を持つものはなく、合成は単体テストだけで確かめた。
- **縁の扱い。** トリミングした画像は縁まで不透明な画素があるので、補間で画像の外を透明として混ぜると縁が半透明ににじむ。画像の内側は端の画素で止めて補間するようにした。

## 5. `overrides` に採用した構造

### 5.1 採用した形

```json
"transform": { "x": 10, "y": -20 },
"overrides": {
  "transform": [
    { "when": { "pose": { "arm.right": "pocket" } }, "transform": { "x": 30 } },
    { "when": { "view": "front", "pose": { "arm.left": "down", "arm.right": "pocket" } }, "transform": { "x": 50, "rotation": 5 } }
  ]
}
```

- `overrides.transform` は `{ when, transform }` の配列。`overrides` の他のキーは予約で、解釈せず保持する。
- `when` には `view` と、`pose` の領域ごとの状態を書ける。**書いたキーだけを照合する**（書かないキーには依存しない）。少なくとも 1 つは書く。
- 現在の状態に当てはまる補正のうち、**条件のキーの数が最も多いもの**を使う。それが基本の `transform` を**置き換える**。当てはまるものがなければ基本の `transform`。
- **キーの数が等しく、同じ状態に同時に当てはまりうる 2 つの補正は INVALID。** JSON だけで判定できる。したがって、どの状態でも適用される補正は 1 つに決まり、配列の並び順は結果に影響しない。

### 5.2 決定論的に一意に決まること

- 選び方は「当てはまるもののうちキーの数が最大」。同数の候補が同時に当てはまることは、読み込み時の検証で排除している。
- テスト：5 つの状態で、補正の並び順を逆にしても結果が同じ。重複する組（`{ view: front }` と `{ pose: { arm.right: pocket } }`、同じ条件の重複）は INVALID。キーの数が違えば有効。
- この規則は実際に役に立った：検証用に書いた fixture が `{ pose: { arm.right: pocket } }` と `{ view: side_left }` を並べており、「横向きで右腕がポケット」のときにどちらを使うか決まらない、と検証器に拒否された。
- 編集の操作（`setTransformOverride`）も、一意に決まらなくなる補正の追加を拒否する。UI から読み込めない Character を作ることはない。

### 5.3 他の案を採用しなかった理由

| 案 | 形 | 採用しなかった理由 |
| --- | --- | --- |
| 文字列の連結キー | `"front\|stand\|down\|pocket": { … }` | 指示書が前提にしないとした形。領域や軸が増えるたびにキーの書式が変わり、「右腕のポーズだけに依存する」を書けない（左腕と胴体の全組み合わせを列挙することになる） |
| 全キー必須の配列 | `when` に VIEW と 3 領域をすべて書く | 一意性は自明だが、上と同じく列挙が必要。腕の状態が 4 つずつになると、帽子の補正 1 つに 16 件要る |
| 入れ子のマップ | `{ "front": { "arm.right": { "pocket": { … } } } }` | 軸の順序を構造に埋め込むことになり、VIEW に依存しない補正を書くのに全 VIEW を列挙する必要がある |
| Asset の具体度と同じ順位付き比較 | キーの種類に優先順位を付ける | 補正では「VIEW と ポーズのどちらが上位か」に根拠がない。数だけで比べ、同数の重なりは作者に解かせる方が、規則が小さく説明しやすい |
| 当てはまる補正をすべて重ねる | 基本 → 条件 1 → 条件 2 と差分を合成 | 順序と合成方法の規定が要り、結果を 1 件ずつ追わないと分からない。「一意に決まる」が「一意に計算できる」に弱まる |

### 5.4 判断が必要な点

- **置き換えか、差分か。** 置き換えは結果が読みやすい反面、「このポーズのときだけ 10 px ずらす」を書くには基本の値を写す必要がある。UI は、条件別の補正を初めて作るときに基本の値を写して始めるようにした（リンク解除時に色を写すのと同じ考え方）。
- **`when` の知らないキーを拒否すること。** 将来、条件に表情などを足すと、古い実装はその Character を INVALID として読めなくなる。Character Schema の他の部分は「知らないものは保持して UNRESOLVED」に寄せているので、ここだけ厳しい。無視すると条件の意味が変わるため、今は拒否にしてある。

## 6. UNRESOLVED と Export の検証

指示書 §9 の暫定の挙動を実装し、ブラウザとテストで確かめた。

| 状態 | 画面 | PNG 出力 |
| --- | --- | --- |
| VALID | 緑の「VALID」 | できる |
| UNRESOLVED：Part の不足 | 「UNRESOLVED」、未解決の理由、Parts の先頭に「不足している Part」（[images/app_missing.png](images/app_missing.png)） | **できる**。注意を表示する。不足 Part 以外は、不足のないキャラクターと画素単位で同じ画像になる |
| UNRESOLVED：実装が知らないポーズ | 「UNRESOLVED」、「描画と PNG 出力ができない」と理由 | **できない**（ボタンが無効）。プレビューも空にする |
| INVALID | 読み込まない。現在のキャラクターをそのまま表示し、理由を出す | 対象外 |

描画できるかどうかは core の `canRender` が決める。現在、描画を止めるのは未知のポーズだけである。

**所見**：

- この線引きは実装上も自然だった。未知のポーズでは腕グループの置き場所が決まらず、描画計画そのものが作れない。Part の不足は、描画計画の中で 1 つの Part が「不足」になるだけで、他に影響しない。
- 知らない VIEW と、素体にない fit は「描画できる」側に入れてある。ただし現在の素材は `front` しかないので、他の VIEW を選ぶと全 Part が「非対応」になり、**何も描かれていない PNG が出力できてしまう**。エラーではないが、利用者には意味のない結果である（§7 の 5）。
- 不足 Part があるときの PNG は「不足している Part が描かれていない絵」になる。それを注意だけで許すのは、指示書の方向性どおりで妥当だと考える。書き出したファイルには、不足があったことは残らない。

## 7. Schema 草案 0.2 で使いにくかった点

実際に UI から使って気づいたこと。Schema の問題と、core の API の問題を分けて書く。

### Schema に関わるもの

1. **条件別の補正が未定義だった**（草案 0.2 の `overrides` は予約）。§5 の形を定義した。
2. **`pivot` の既定値がキャンバス中央であること。** Schema というより Asset 仕様 §9 の規定だが、Part 単位の拡大・回転には使いにくい（§4.2）。
3. **共有色を「未設定に戻す」方法がない。** 新規作成時は `sharedColors` が空で、リンクしているスロットは Part の既定色を使う。一度設定すると、キーを消す操作がないので未設定には戻せない。Schema は表現できる（キーを書かなければよい）ので、操作を足すかどうかの問題である。
4. **読み込まれていない Part は category が分からない。** 1 Part だけの category で別の Part を選んでも、不足している Part は自動では外れない。後でその Part が読み込まれると、category の重複（注意）として現れる。草案 0.2 の規則（重複は保持して両方描画）の範囲に収まっているが、起こりうる経路として記録しておく。
5. **「何も描かれない VALID」がありうる。** 素材のない VIEW を選んだ場合など（§6）。Character は正しく、Part がすべて非対応になるだけなので、3 状態では表せない。

### core の API に関わるもの（Schema は変えなくてよい）

- `equipPart` は Character だけを返すので、UI が「いま装備した Instance」を知るには探し直す必要があった。
- Part を選ぶときの「同じ category を外す」は、Part の manifest が要るので core の Character 操作には置けず、`src/app/session.ts` に置いた。UI を作り直しても使えるよう、DOM に依存しない形にしてある。
- 名前・VIEW・fit の解除に当たる操作がなく、最初は UI から Character を直接組み立てていた。指示書 §6 に反するので、`rename`・`setView`・`setFit(…, undefined)` を core に足した。

使いやすかった点も記録する：Instance の色の形（`{ linked?, color? }`）は UI の部品とそのまま対応し、変換が要らなかった。`equipped: false` で Instance を残す設計は、Part を切り替えて戻したときに色と位置が戻る挙動を、追加の実装なしで与えた。

| 6 | Asset 仕様 §9 または UI 挙動の文書 | `pivot` の扱い。既定値は変えず、UI が Part の位置（画像の外接矩形の中心など）から `pivot` を補って保存する | 未反映。Phase 1-C で UI と合わせて決める |

草案 0.2 から**変えなかった**もの：全体構造、`canvas`、`appearance`、Equipment Instance の必須項目、色、`state`、`requirements`、前方互換性の方針、3 状態の境界。UI から使っても、これらを変える理由は見つからなかった。

## 9. RC1 にできるかの実装側評価

**構造は RC1 にできる水準にあると考える。** 根拠：

- 草案 0.2 の必須項目と意味論は、UI を一通り作っても変更が要らなかった。
- 新しく定義したのは、予約だった `overrides` の中身だけである。追加であって、草案 0.2 の Character はそのまま有効である。
- 保存 → 読込の一致、不足 Part の保持、3 状態の境界は、core のテストに加えて実ブラウザの経路でも成立した。

ただし、RC1 にする前に次の 6 点の判断が要る。いずれも草案 0.3 候補では実装側の選択で仮に決めてある。

| # | 判断が必要な点 | 候補の選択 | 変えた場合の影響 |
| --- | --- | --- | --- |
| 1 | 条件別の補正は、置き換えか差分か | 置き換え | 差分にするなら合成の順序を規定する必要がある。保存済みデータの意味が変わるので、RC1 の前に決める |
| 2 | 補正の選び方 | キーの数が最大のもの。同数の重なりは INVALID | Asset の具体度と揃えるなら、キーの種類に順位を付ける |
| 3 | `when` の知らないキー | INVALID | 「保持して、その補正は当てはまらないものとして扱う」にもできるが、条件が緩く解釈される危険がある |
| 4 | Part 既定との合成方法 | 加算・乗算・`pivot` は Instance 優先 | Asset 仕様 §9 に書くか、Character Schema に書くか |
| 5 | UNRESOLVED での書き出し | 描画できれば注意つきで可、未知のポーズでは不可 | 「何も描かれない PNG」を止めるかどうかも合わせて決める |
| 6 | `pivot` の既定値 | キャンバス中央のまま（UI で補う） | 既定値を変えるなら Asset 仕様の変更になる |

1〜3 は保存データの意味に関わるので、RC1 の前に確定する必要がある。4〜6 は RC1 の後でも、文書の追記と UI の対応で扱える。

## 10. Phase 1-C 以降への持ち越し

- **`pivot` の UI**：編集、または Part の位置からの自動設定。
- **Transform のドラッグ操作**、Undo / Redo。
- **配置補正のある描画の、ブラウザと参照実装の差の実測**（許容差の定義）。
- **正面以外の VIEW**：素材がないので、条件別の補正の `view` は値の照合だけを確かめた。実際の絵での検証は素材ができてから。
- **共有色を未設定に戻す操作**、素体の入れ替え（現在は未対応として例外にしている）。
- **UI 挙動の文書**：重複装備の防止、不足 Part の案内、UNRESOLVED での書き出し、何も描かれない場合の扱い。
- **保存先**：現在はファイルのダウンロードと選択だけ。IndexedDB などは未着手。
- **Capability の正式仕様**、`.impart` の読み込み、VARIANT、PORTRAIT、一括出力（指示書 §12）。
- **スマホ実機での性能試験**（Phase 0 からの持ち越し）。
- **UI の技術選定**：最小 UI は約 470 行の素の DOM で、画面を毎回作り直している。機能が増えると、入力中の部品を保つための分岐（現在は色の入力だけ）が増える。拡張の前に選定するのがよい。

## 12. 決定記録（2026-10-05）

§9 の判断事項に対する決定と、RC1 への反映。

| # | 項目 | 決定 |
| --- | --- | --- |
| 1 | 条件別の補正は置き換えか差分か | **置き換え。** その状態でどう配置するかが 1 件を見れば確定することを優先する。後から基本の補正を変えても、調整済みの状態がずれない |
| 2 | 補正の選び方 | **条件のキーの数が最大のもの。** 同じ数で同時に当てはまりうる組は INVALID。Asset の具体度とは揃えない（目的が違い、VIEW とポーズのどちらが上位かに普遍的な順位がない） |
| 3 | `when` の知らないキー | **INVALID。** 無視すると条件の意味が変わる。未知のフィールドを保持する原則は、条件式である `when` には適用しない |
| 4 | Part 既定との合成方法 | **位置と回転は加算、拡大縮小は乗算、`pivot` は Instance 側を優先。** Asset 仕様 §9 に規定し、Character Schema からは参照する |
| 5 | UNRESOLVED での書き出し | **描画できれば注意つきで可、描画の意味が決まらなければ不可**を正式にする。加えて**描画される Layer が 0 枚なら不可**。4 つ目の状態は作らず、書き出しの事前条件として扱う |
| 6 | `pivot` の既定値 | **変えない。** Phase 1-C で、UI が Part の見た目の中心を最初の `pivot` にする、直接編集する、などを検討する |

配置補正のある描画の許容差は決めず、Phase 1-C 以降の実測事項として残す。

RC1 に合わせた変更：

- Character Schema：【要判断】を確定事項にし、§10.2.1（画像の書き出し）と §12（草案からの経緯）を加えた。
- Asset 仕様 §9：差分としての合成の計算を規定した（§15 に「RC1 以後の修正」として記録）。
- 実装：描画される Layer が 0 枚のときは PNG を出力できないようにした（`src/app/session.ts`）。テストとスモークテストに、素材のない VIEW と、素材が読み込まれていない環境の場合を足した。

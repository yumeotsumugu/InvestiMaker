## 1. 製品の目的

InvestiMakerは、TRPGで使う2Dキャラクターを、専用ソフトのインストールや画像編集ソフトの知識なしで作成できるブラウザアプリケーションである。

目標は「キャラクターを作れる」だけではない。ユーザーが迷わずキャラクターを組み立て、表情・衣装・ポーズ等の差分を作り、立ち絵やアイコンとしてセッションへ持ち出せるところまでを一つの体験として提供する。

### 1.1 ブランド上の最重要原則

InvestiMakerは次の二つの利用方法を**同等の正式な利用形態**として扱う。

``` text
Web版
GitHub Pages等の静的ホスティングへアクセス
        │
        ├──→ InvestiMaker
        │
ローカル版
GitHub等からZIPをダウンロード
→ ZIPを解凍
→ index.htmlをダブルクリック
```

利用者に以下を要求してはならない。

-   インストーラーの実行
-   Node.js / npm の導入
-   VS Code等の開発環境
-   ローカルWebサーバーの起動
-   コマンドライン操作
-   アカウント登録やログイン（基本機能）

**「ZIPを解凍してindex.htmlを開けば使える」ことを製品要件とする。**

### 1.2 ローカルファースト

キャラクターデータ、素材の合成、色変更、画像生成、保存データの生成は原則としてユーザーのブラウザ内で完結する。

標準機能のためにキャラクターデータや生成画像を外部サーバーへ送信しない。Web版もローカル版も、この原則を共通とする。

## 2. 製品形態と配布

### 2.1 単一製品・単一成果物

Web版とローカル版を別製品として実装しない。

本番ビルドで生成された**同一の配布成果物**が、静的HTTP環境と`file://`直接起動の両方で動作することを基本とする。

``` text
source
  │
  └─ build
       │
       └─ distribution/
           ├─ index.html
           ├─ assets/ ...
           └─ 必要な静的ファイル
                │
                ├─ GitHub Pagesへ配置
                └─ ZIPとして配布
```

`standalone/index.html`のような別製品を恒久的に維持することは最終形としない。開発・検証用の一時成果物として存在することは許可する。

### 2.2 ローカル配布の完成条件

配布ZIPについて、ユーザーは次だけで利用開始できなければならない。

1.  ZIPをダウンロードする。
2.  ZIPを解凍する。
3.  ルートの`index.html`をダブルクリックする。
4.  Chrome / Edge等の対応ブラウザでInvestiMakerが起動する。

READMEを読まないと起動できない構造は不可とする。

### 2.3 Web配布の完成条件

同じ配布成果物をGitHub
Pages等の静的ホスティングへ置くだけで利用できること。

サーバーサイドAPI、データベース、サーバーレンダリングを基本機能の前提にしない。

### 2.4 オフライン利用

ローカル版は、標準素材を含む基本機能について**インターネット接続なしで利用可能**であることを完成条件とする。

外部URLから標準素材・フォント・JavaScript・CSS等を実行時取得する設計を基本としない。

## 3. 技術アーキテクチャ原則

### 3.1 開発環境と配布環境を分離する

開発者はVite / TypeScript /
npm等を利用してよい。しかし、それらは利用者の実行条件ではない。

``` text
開発
src/ + npm run dev
        │
        └─ build
             │
             └─ 利用者向け静的成果物
```

### 3.2 `file://`互換性を最初から守る

製品コードは「HTTPサーバーが存在する」ことを暗黙の前提にしない。

特に以下を設計・ビルド時に確認する。

-   ES Moduleの読み込み方式
-   `fetch()`によるローカルJSON/素材取得
-   Worker等のブラウザ制限
-   相対パス
-   Canvasへの画像読み込み
-   CORS / origin依存処理
-   動的import
-   外部CDN

必要なmanifestや小規模なメタデータはビルド時にバンドルしてよい。画像等を別ファイルで配置する場合も、直接起動で読み込める方式を採用する。

### 3.3 ブラウザ互換性

v1の正式対応対象はデスクトップ版の現行Chrome / Edgeを基本とする。Firefox
/ Safariは検証結果に応じて対応範囲を定める。

スマートフォン向け完成UIは後続フェーズとするが、データ仕様をモバイル非対応に固定しない。

### 3.4 ディレクトリ責務

-   `src/core/`：DOM非依存。Character操作、評価、描画計画等。
-   `src/web/`：ブラウザ依存の共通処理。
-   `src/app/`：製品Creator UI。
-   `src/minimal/`：Phase
    1-B最小UIの検証用リファレンス。恒久維持は必須ではない。
-   `src/lab/`：Renderer / Core検証環境。
-   本番配布物：開発用ページを含める必要はない。

## 4. データとプライバシー

### 4.1 Characterを唯一の正本とする

キャラクターの装備、色、fit、VIEW、POSE、EXPRESSION、Transform、装備順等はCharacterデータを正本とする。

PreviewやUIコンポーネントが独自のキャラクター状態を持たない。

### 4.2 保存

v1ではCharacter
JSONのダウンロード/読み込みを正式なバックアップ・移動手段とする。

将来、IndexedDBによる自動保存を導入する。ただしIndexedDBだけに依存せず、ユーザーがファイルとしてバックアップできる経路を常に持つ。

将来的な`.imchar`はCharacterと再配布可能なカスタム素材を自己完結して持てる形式の候補とする。

### 4.3 ブラウザ内処理

以下は原則クライアントサイドで行う。

-   Character編集
-   素材合成
-   色変更
-   Transform
-   Portrait / Composition
-   PNG生成
-   ZIP生成
-   Character保存/読込
-   `.impart`検証・導入（後続）

## 5. データモデル

概念を以下のように分離する。

| 層 | 役割 |
| --- | --- |
| APPEARANCE / CHARACTER | 誰なのか。素体・顔・髪等の基本外見 |
| OUTFIT | 衣装・靴・帽子・眼鏡・アクセサリー |
| EXPRESSION | 目・眉・口の状態 |
| POSE | 胴体・左右腕等の状態 |
| VIEW | 正面・斜め・横等 |
| ITEM | 持ち物。複数選択可 |
| OVERLAY | 傷・汚れ・効果等。複数選択可 |
| VARIANT | 上記軸の組合せに名前を付けるショートカット |
| COMPOSITION | 全身・膝上・腰上・胸上・顔等の構図 |
| PORTRAIT | アイコン用構図・背景・枠等 |
| EXPORT | 出力形式・サイズ・命名・一括出力 |

Character Schema v1
RC1を保存形式の正本とし、UI都合で別の意味論を追加しない。

## 6. 素材システム

Asset Specification v1 RC1を素材規格の正本とする。

-   マスターキャンバス：1600×2400。
-   標準画像：8-bit RGBA PNG / sRGB / non-premultiplied。
-   Part → Layer → Asset → Mask / ColorSlot。
-   左右は独立して扱える構造を持つ。
-   正面・斜め・横は原則専用素材。
-   Part既定TransformとInstance補正の合成はAsset Specification
    §9に従う。
-   カスタム素材に任意JavaScript / HTML / 実行ファイル /
    外部URL実行を許可しない。

### 6.1 ユーザー追加素材

後続フェーズで`.impart`を導入する。

`.impart`はZIPコンテナとし、画像＋宣言的JSONを基本とする。導入後もWeb版/ローカル版双方で同じCharacterから利用できる設計を目標とする。

------------------------------------------------------------------------

## 7. 製品フロー

最終的な主要フローを次の5段階とする。

``` text
CREATE → CUSTOMIZE → VARIANT → PORTRAIT → EXPORT
```

### CREATE

キャラクター名と素体を選び、編集可能なCharacterを生成する。性別・年齢を必須属性として先に質問しない。素体を選んだ結果として外見が決まる。

### CUSTOMIZE

素体、顔、髪、服、装飾、表情、ポーズ・向き、その他を編集する。

### VARIANT

表情・衣装・ポーズ・VIEW・ITEM等の組合せを名前付きで保存する。同じキャラクターを複製して差分管理しない。

### PORTRAIT

Character自体を変えず、顔アイコン・バストアップ等の構図を作る。ズーム、X/Y、形状、背景、枠等を保存する。

### EXPORT

立ち絵、Portrait、差分等を用途別に出力する。

## 8. Creator UI

Phase 1-Cで確定した案Bを基本レイアウトとする。

``` text
┌──────────────────────────────────────────────────────────────────────┐
│ InvestiMaker   Character name                         保存 読込 設定 │
├────────┬───────────────┬─────────────────────┬───────────────────────┤
│ 大分類 │ Part/状態選択 │       PREVIEW       │ 選択対象の設定        │
│        │               │                     │                       │
│ 素体   │               │                     │ 色                    │
│ 顔     │               │                     │ Advanced              │
│ 髪     │               │                     │                       │
│ 服     │               │                     │                       │
│ …      │               │                     │                       │
├────────┴───────────────┴─────────────────────┴───────────────────────┤
│ CREATE     CUSTOMIZE       VARIANT       PORTRAIT       EXPORT       │
└──────────────────────────────────────────────────────────────────────┘
```

内部のPart ID、Instance
ID、category、UNRESOLVED等を通常UIへ露出しない。必要な内部情報はAdvancedへ隔離する。

### 8.1 色

Character Schemaの`sharedColors`、Instance
colors、`linked`を利用する。UI独自の色モデルを作らない。

### 8.2 表情

標準表情プリセットをUIに出すが、保存するのは実際の目・眉・口stateである。個別変更でプリセットから外れた場合は「カスタム」と表示する。

### 8.3 ポーズ・VIEW

胴体・左右腕を個別に編集する。VIEWは「ポーズ・向き」内で扱う。素材が存在しない状態や互換性問題は人間向けの文章で案内する。

### 8.4 Advanced

Transform、条件別Transform、pivot、必要な内部情報を扱う。通常利用者がAdvancedを開かなくても基本キャラクター作成を完了できることを原則とする。

## 9. エラー・互換性・通知

CharacterのVALID / INVALID / UNRESOLVEDという意味論はCharacter
Schemaに従うが、通常UIでは人間向けに翻訳する。

-   描画可能な不足素材：注意を出しつつ編集・保存・PNG出力を許可。
-   描画不能：原因を案内しPNG出力を無効化。
-   INVALID読込：現在Characterを置き換えず拒否。
-   描画Layer 0枚：Character状態とは別のExport事前条件として出力不可。

通知によってPreviewの表示倍率・大きさが変化しないUIを完成条件とする。

## 14. Phase 3 --- TRPG Workflow

Phase 3でInvestiMaker固有のTRPG向け価値を完成させる。

## 17. リポジトリと公開形態の最終イメージ

開発リポジトリはソース・仕様・テストを保持する。一方、利用者が取得する配布ZIPは開発環境を要求しない。

``` text
Repository
├─ src/
├─ docs/
├─ tests/
├─ package.json
├─ ...development files
│
└─ build
    ↓
Distribution
├─ index.html
├─ assets/
└─ other static runtime files
```

GitHub PagesはDistributionを公開する。

Download
ZIPについては、**ユーザーが取得するZIPのルートに実行可能な`index.html`が存在すること**を必須とする。

GitHubの「Source code (zip)」やリポジトリの「Download
ZIP」をそのままユーザー導線に使う場合は、リポジトリのルート構成自体がこの要件を満たす必要がある。そうでない場合はRelease
Assetとして利用者向けZIPを生成する。

どちらを採用しても、ユーザー体験は次で統一する。

``` text
Download
→ Extract
→ index.html
→ Start
```

ローカル版をネットワークなしの状態で開き、標準素材を使った主要操作が完了することを確認する。

## 19. 設計上の禁止事項

最終製品の基本機能について、次を避ける。

-   `npm run dev`を利用者向け手順にする。
-   ローカルサーバーの起動を利用者へ要求する。
-   Web版だけでしか使えない基本Creator機能を作る。
-   ローカル版だけ別コードベースとして維持する。
-   CDNが落ちるとローカル版が起動しない構造にする。
-   Characterや生成画像を無断で外部送信する。
-   UI状態をCharacterの第二の正本にする。
-   未知の素材や状態を推測してデータを破壊する。
-   ユーザー追加素材から任意コードを実行する。

## 21. 最終原則

InvestiMakerの価値は、高機能であることだけではない。

**「URLを開けば使える。気になるならZIPを落として、解凍して、index.htmlを開けば使える。」**

この簡単さを、機能追加より下位の都合で失わない。

Web版とローカル版は同じInvestiMakerであり、ユーザーは環境構築を意識しない。TRPGの立ち絵を作りたい人が、ツールを使うための準備ではなく、キャラクターを作ることそのものに時間を使える製品を最終着地とする。

# InvestiMaker Phase 0 検証プロトタイプ 作業指示書

対象：このリポジトリで作業する Claude Code
作成日：2026-10-05

---

## 1. このプロジェクトについて

InvestiMaker は、TRPG 用の 2D キャラクター立ち絵・差分・アイコンを、既製パーツの組み合わせで作るブラウザツールです。サーバーを持たない完全クライアントサイドのアプリで、将来は第三者が自作パーツ（`.impart`）を追加できる公開規格を持ちます。

素材規格は `docs/specifications/InvestiMaker_Asset_Specification_v1.md`（以下「仕様書」）に草案 0.2 として書かれています。設計方針は承認済みですが、§13 に 9 件の未確定事項が残っており、机上では決められません。

**今回の目的は、仮素材 1 セットと最小の合成実装を作り、§13 を確定するための材料を出すことです。** 製品の UI を作る段階ではありません。成果物は「動く検証ページ」と「検証レポート」です。

## 2. 最初に読むもの

1. `docs/specifications/InvestiMaker_Asset_Specification_v1.md` — **唯一の正**。全文を読んでください。
2. `docs/design/` の基本設計書 v0.1 — 背景理解用。作成後に方針が変わっており、食い違う箇所は仕様書が優先です。主な変更点：
   - VARIANT は継承を持たず、7 軸（APPEARANCE / OUTFIT / EXPRESSION / POSE / VIEW / ITEM / OVERLAY）の選択状態に名前を付けたものになった。
   - レイヤーは固定順の一覧ではなく、Part → Layer → Layer Slot の構造になった。
   - 色変更は Mask 方式になった。

基本設計書が `.docx` で置かれている場合は、内容を Markdown に起こして `docs/design/InvestiMaker_Basic_Design.md` として保存してください。

## 3. 守ること

- **仕様書を黙って書き換えない。** 実装中に矛盾・不足・実現困難な点を見つけたら、実装側で妥当な解釈を選んで進め、その内容を検証レポートの「仕様への変更提案」に記録してください。仕様書の修正は人間が判断します。
- **仕様書にない推測でフォールバックしない。** 特に Asset 解決（§6.5）は、規定の手順以外で画像を選ばないことがこの規格の中心です。
- **他サービスの画像・コード・UI を流用しない。** 仮素材はすべてこのリポジトリ内のスクリプトで生成します。
- **実行時に外部通信をしない。** CDN、外部フォント、解析タグは使いません。
- 依存パッケージは最小限にしてください。追加するときは理由をコミットメッセージに書いてください。
- `git init` とコミットは行ってかまいません。リモートの作成と push は指示があるまで行わないでください。

## 4. 技術構成

- Vite + TypeScript（strict）。UI フレームワークは使わず、素の DOM で書きます。検証ページは使い捨てになる可能性が高く、製品 UI の技術選定は別途行うためです。
- テストは Vitest。
- 合成は Canvas 2D。色変更は `getImageData` による画素演算で実装し、結果をキャッシュします。WebGL は今回使いません。
- **合成・解決・検証のロジックは DOM に依存しない純粋な関数として `src/core/` に置いてください。** この部分は製品版にそのまま持ち越します。

## 6. 作業内容

順番に進め、各ステップの完了ごとにコミットしてください。

### ステップ 1：土台

リポジトリの初期化、上記の構成、Vite / TypeScript / Vitest の設定、README（目的と起動方法）。

### ステップ 2：core の実装

| モジュール | 内容 | 仕様書 |
|---|---|---|
| manifest 型 | Part / Layer / Asset / Mask / ColorSlot / Body の TypeScript 型 | §1, §5, §7, §8, §11 |
| manifest 検証 | 必須フィールド、ID 書式、slot と category の存在、channels の参照先、`when` の重複検出 | §3, §11.1, §12 |
| Asset 解決 | Context から Layer ごとの Asset を決める。未解決と Part 非対応の判定を含む | §6.4, §6.5 |
| 描画順 | Layer Slot の標準順、腕グループの挿入位置、`zBias`、`hides` | §6.1, §8 |
| 色合成 | `tint` / `multiply` / `fixed` と適用率による合成 | §5.3 |
| 互換性判定 | `compatible` / `requires` / `conflicts` から 不足・非対応・競合 を返す | §8 |

ZIP の読み込み、SVG、`mirrorable` による反転、Transform は今回の対象外です。型にフィールドだけ用意し、実装は残してかまいません。

### ステップ 3：適合性テスト

- 仕様書 §6.6 の **T1〜T12 をすべて `tests/conformance/` にテストとして書き、通してください。** 不正とされるケース（T7・T8・T10）は、検証が拒否することを確認します。
- テスト入力は manifest の JSON 断片としてファイルに置いてください。将来 `.impart` の適合性テスト素材に発展させるためです。
- 色合成は単体テストで式を固定してください。最低限：下地 `#808080` に `tint` で指定色そのものになる／下地が黒なら黒／下地が白なら白／適用率 0 で元色のまま／適用率 50% で中間／アルファが変化しない。

### ステップ 4：仮素材の生成

`tools/` に、仮素材一式を**決定的に**生成するスクリプトを作ってください（同じ入力なら同じ出力）。出力先は `assets/development/<Part ID>/` で、中身は `.impart` を展開した形（`manifest.json` + `preview.png` + `assets/`）にします。

- 絵としての品質は求めません。単純な図形でかまいませんが、**検証に必要な性質は持たせてください**：
  - 色変更領域は 50% グレー基準で、影（暗い部分）とハイライト（明るい部分）を含む。
  - 線画に相当する暗色の輪郭があり、Mask 値は 0。
  - Mask の境界はアンチエイリアスされている（適用率が中間値になる画素がある）。
  - トリミングして `offset` を付ける。
- namespace は `dev` を使います（`im` は公式専用のため）。
- キャンバスサイズは引数で変えられるようにしてください。既定は 1600×2400。

必要な Part：

| Part | 検証したいこと |
|---|---|
| 素体 `dev.body_adult_standard` | `body.base`、左右の腕と手、anchors、`skin.base` へのリンク、`fitDimensions.chest`、右腕のポーズ `down` と `pocket` |
| 顔：輪郭・耳・鼻 | 頭部グループの重なり |
| 目・眉・口 | §6.3 の標準状態をすべて持つ。`state` による解決 |
| 前髪・後髪 | `hair.base` の共有カラー。眉と前髪の前後関係 |
| シャツ `outfit.top` | 身頃＋左右の袖。袖は `down` と `pocket` の両方。`chest: large` 専用の身頃 |
| ボトムス・靴下・靴 | 裾と靴の重なり |
| コート `outfit.outer` | 後ろ身頃・前身頃・左右の袖。3 色スロット。**袖は `down` のみ**（`pocket` で Part 非対応になることの確認用） |
| 帽子 `outfit.head` | `outfit.head.back` と `outfit.head` の 2 Layer。`hides` |
| メガネ `outfit.eyewear` | 前髪との前後関係 |
| 赤面 `overlay` | `overlay.face` の位置 |

### ステップ 5：検証ページ（`src/lab/`）

`npm run dev` で開ける 1 ページです。見た目は簡素でかまいません。

- プレビュー（合成結果）と PNG 書き出し（透過）。
- 操作：Part の着脱、表情の切り替え、右腕ポーズ（`down` / `pocket`）、胸部 fit、共有カラーと各 ColorSlot の色、共有カラーのリンク解除。
- **解決結果の一覧**：描画順に、Layer Slot・Part・選ばれた Asset のファイル名・状態（描画 / 省略 / 未解決）を表で表示。非対応・競合の Part は理由を表示。
- **計測表示**：初回合成時間、色変更後の再合成時間、読み込んだ画像の総画素数から見積もったメモリ量。
- **比較用の切り替え**：
  - 眉を前髪の前 / 後ろに置く。
  - 靴をボトムスの下（`outfit.shoes`）/ 上（`outfit.shoes.over`）に置く。
  - 色合成モード `tint` / `multiply`。

### ステップ 6：検証レポート

`docs/reports/Phase0_Verification_Report.md` を作成してください。§13 の 9 項目それぞれについて次を書きます。

- 何を試したか。
- 得られた事実（計測値、スクリーンショットや書き出し画像へのパス）。
- 推奨と、その根拠。
- **人間の目で判断が必要な点**（発色の好み、重なりの違和感など）は、判断材料を示したうえで未決のまま残す。

特に確認してほしいこと：

| §13 | 確認内容 |
|---|---|
| 1 キャンバス | 1200×1800 / 1600×2400 / 2000×3000 で仮素材を生成し、合成時間とメモリ見積もりを比較。 |
| 2 `tint` 基準 | 明色・暗色・高彩度色・肌色を指定したときの書き出し画像を並べる。50% グレー基準で暗色が潰れないか、明色が白飛びしないか。 |
| 3 Mask の A | A チャンネルに値を入れた Mask を Canvas 経由で読み、RGB の値が保持されるか実測。 |
| 4 描画順 | 仮素材で重なりが破綻する組み合わせがないか。上記の比較切り替えの結果。 |
| 5〜9 | 実装して気づいた範囲で所見を書く。試していない項目は「未検証」と明記。 |

最後に「仕様への変更提案」の節を設け、実装中に見つけた矛盾・不足・曖昧さを、該当する節番号と提案内容の形で列挙してください。

## 7. 今回やらないこと

保存 / 読込（JSON、IndexedDB）、`.impart` の ZIP 読み込み、SVG、正面以外の VIEW、ITEM、COMPOSITION / PORTRAIT、VARIANT、Undo / Redo、Advanced Mode、製品としての UI デザイン、JSON Schema の作成。

これらに手を付けたくなった場合は、実装せずレポートに提案として書いてください。

## 8. 完了条件

- `npm test` がすべて通り、T1〜T12 が含まれている。
- `npm run dev` で検証ページが開き、仮素材でキャラクターが合成され、PNG を書き出せる。
- 右腕を `pocket` にするとコートが「非対応」と表示され、コートの Layer が 1 枚も描画されない。シャツは `pocket` 用の袖で正しく描画される。
- 色を変えても線画の色が変わらない。
- 仮素材が生成スクリプトから再生成できる。
- 検証レポートがあり、§13 の各項目に「検証済み（結果）」「未検証」「人間の判断待ち」のいずれかが明記されている。

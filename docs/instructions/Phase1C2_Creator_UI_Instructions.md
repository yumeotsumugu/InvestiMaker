## 0. 目的

Phase 1-B の最小 UI を、利用者が内部の仕組み（JSON、Part ID、Instance、Layer、Transform）を知らなくても使える **Creator UI** に置き換える。対象は CREATE と CUSTOMIZE、および 1 枚の PNG を出す EXPORT である。

見た目を整えることが目的ではない。**ワイヤーフレームで確定した配置と操作を、そのまま動くものにする。** 色・書体・余白は読みやすい程度でよい。

## 1. ブランチ

`phase1c-creator-ui` を main から作成する。Phase 1-C-2 の完了までは main へマージしない。

## 2. 変えないもの

- **Asset Specification v1（RC1）と Character Schema v1（RC1）の意味論は変えない。** 実装中に仕様の不足や矛盾を見つけたときは、**既存の仕様から一意に解釈できる場合のみ実装する。複数の意味論が成立し、Asset Specification / Character Schema / 保存互換性に影響する場合は独断で確定せず、実装を保留して検証レポートへ記録する。**
- **Character が唯一の正本**である。UI 用の第二の正本を持たない。編集は `src/core/character/operations.ts`、評価は `evaluate.ts`、描画計画は `planCharacter` を使う。DOM から Character を直接組み立てない。
- `src/core/` は DOM に依存しない。`src/web/` はブラウザに依存する共通処理、`src/app/` は製品 UI、`src/lab/` は検証環境。
- 実行時に外部通信をしない。UI フレームワークは導入しない（素の DOM と TypeScript）。
- 依存パッケージは増やさない。必要になった場合は理由をコミットメッセージに書く。

## 3. 構成

```text
src/app/              Creator UI（今回作るもの）
├─ main.ts            起動と、段（CREATE / CUSTOMIZE / EXPORT）の切り替え
├─ session.ts         UI の操作（DOM 非依存）。Phase 1-B のものを拡張する
├─ catalog.ts         分類の構成（大分類・小分類と category の対応、なくせない分類）
├─ labels.ts          表示名の辞書（分類・状態・ポーズ・向き・注意の文）
├─ messages.ts        内部の状態やコードを、利用者向けの文にする
└─ views/             画面の部品（ヘッダー、段の帯、分類の列、一覧、プレビュー、編集パネル、各段）
```

ファイルの分け方は目安である。より自然な分け方があれば変えてよい（理由をレポートに残す）。

**Phase 1-B の最小 UI は残す（確定）。** `src/minimal/` と `minimal.html` に移し、`index.html` を Creator UI にする。`src/lab/` は Renderer と Core の検証環境、`src/minimal/` は「Phase 1-B 時点の Character 操作 UI のリファレンス」という役割である。既存のスモークテスト（`npm run smoke:app`）は `smoke:minimal` に名前を変えて最小 UI を対象にし続け、Creator UI 用に `smoke:creator` を新しく作る。Phase 1-C が安定した後に削除するかは、改めて判断する。

## 4. 画面

設計書 §20.1 の 4 列（案 B）を実装する。ワイヤーフレームの各画面が、そのまま実装の対象である。

| 画面 | ワイヤーフレーム | 内容 |
| --- | --- | --- |
| CREATE | 流れ 1 | 名前、素体の選択、「基本のパーツを付けて始める」、保存したキャラクターの読み込み |
| CUSTOMIZE | 案 B、流れ 2〜7 | 大分類の列、選ぶ列、プレビュー、編集パネル |
| EXPORT | 流れ 8・9 | プレビュー、PNG の保存、注意、書き出せないときの理由と直し方 |

- **ヘッダー**：ブランド名、名前（直接編集できる）、保存・読込・設定。問題があるときだけ、名前の横に小さな印を出す。
- **下の帯**：CREATE / CUSTOMIZE / VARIANT / PORTRAIT / EXPORT。VARIANT と PORTRAIT は「準備中」として表示し、押せない。
- **プレビュー**：1600×2400 のキャンバスを、縦横比を保って縮小表示する。透明な部分は市松模様。変更はすぐに反映する。
- 画面の幅が狭いときの配置は今回の対象外。ただし、後で Part の一覧を折り畳めるよう、列の幅を決め打ちした作りにしない。

## 5. 分類と表示名

- 大分類・小分類と category の対応は、`Phase1C1_Wireframes.md` §3 の表のとおりとする。`catalog.ts` に定義し、Asset 仕様の category 一覧（`src/core/ids.ts`）に過不足がないことをテストする。
- 素材が 1 つもない小分類は表示しない。大分類の中身がすべて空なら、その大分類も表示しない。
- **表示名は `labels.ts` の辞書で持つ。** 対象は、大分類、小分類、目・眉・口の状態、ポーズの領域と状態、向き、共有色のキー、fit の次元と値。辞書にない値（素材や保存データが持つ未知の値）は、内部の値をそのまま表示する。
- Part の名前とスロットの名前は、manifest の `name` を使う。
- category の ID、Part ID、Instance ID は、詳細設定（Advanced）と、見つからない素材の表示でだけ出す。

**なくせない分類は、素体・輪郭・目・眉・口の 5 つ（確定）。** これらには「なし」のカードを出さない。鼻・耳・髪・服などは外せる。目のないキャラクターなどを作る場合は、それを表す Part で対応する。

## 6. Part の選択（操作判断 1〜7）

- カードはサムネイル（`preview.png`）と名前。選択中のものが分かるようにする。
- **カードを選ぶと、装備と編集対象の選択を同時に行う**（判断 3）。
- 1 つだけ選べる分類：別のカードを選ぶと入れ替わる。先頭に「なし」のカードを置く（なくせない分類を除く）。選んであるカードをもう一度押しても外れない。
- 複数選べる分類：カードを押すたびに、付ける／外すが切り替わる。同じパーツを 2 つ付ける操作は通常の画面に置かない。
- **外したパーツの Instance は残し、通常の画面には出さない**（判断 5）。選び直すと元の設定で戻る。
- **使えないパーツは薄く表示し、選べなくして理由を添える**（判断 6）。すでに装備していて後から使えなくなったものは、装備したまま注意として知らせる。勝手に外さない。
- **見つからない素材は、注意の一覧にまとめ、そこから外せるようにする**（判断 7）。

**一覧のカードが「使えるかどうか」は、仮の Character と core の判定で求める（確定）。** 候補の Part ごとに「それを装備したと仮定した Character」を作り、core の描画計画で、その Part が対応・非対応・競合のどれになるかを見る。UI 独自の互換性判定は書かない。理由の文は `messages.ts` で作る。

```text
current Character → candidate Character → evaluate / plan → CardState
```

- **実際の Character を一瞬変更して戻す実装にしない。** 判定は副作用のない純粋な処理とする。カードを眺めているだけで、保存していない変更の判定・Instance・装備順に影響が出てはならない。
- 素材が少ないので、候補ごとに毎回評価してよい。**今は最適化しない**（キャッシュなどは、Part が数百になって重くなってから考える）。

## 7. 色（操作判断 8〜11）

- 素体を選ぶと、右ペインに「全体の色」（肌・髪・左目・右目）と体型（fit）を出す。
- パーツを選ぶと、そのパーツのスロットごとの色を出す。全体の色に従っているスロットは「髪色（全体）」のように示し、その場で全体の色を編集できる。
- 「このパーツだけ色を変える」の印で、全体の色から切り離す。**リンクの解除と復帰は必ず `unlinkColor` / `relinkColor` を使う**（解除時に見た目が変わらない挙動を UI で作り直さない）。
- 色の入力は、ブラウザ標準の色選択と 16 進数。最近使った色は UI の一時的な記憶でよい。

**新規作成時の全体の色は、素材の `default` から決定的に作る（確定）。** UI は色の値を持たない。最初の装備を確定した後、**装備順（`equipment` の並び）にたどり、各 Part の ColorSlot を宣言の順に見て、共有色のキーごとに最初に見つかった有効な `default` を採用する。** 同じ初期構成なら、manifest の読み込み順などに関係なく、必ず同じ `sharedColors` になる。

## 8. 表情・ポーズ・向き（操作判断 12〜17）

- **表情**：左に標準表情 6 種と「カスタム」、右に目・眉・口の個別の選択。プリセットを選ぶと 3 つの状態をまとめて設定する。個別に変えて標準表情に当たらなくなったら、左は「カスタム」を示す。いまどのプリセットかは、core の `expressionPresetOf` で毎回求める。
- **ポーズ**：胴体・左腕・右腕を別々に選ぶ。選択肢は Pose Definition から作る。プリセットは出さない。
- **向き**：「ポーズ・向き」の中に置く。素体の manifest の `views` にない向きは「素材なし」として選べなくする。読み込んだキャラクターがその向きだった場合は、そのまま表示し、「向きを正面に戻す」を出す。
- 状態の選択肢は名前のボタンでよい（サムネイルは作らない）。
- ポーズや向きを変えて使えなくなったパーツがあれば、右ペインとプレビューの下で知らせ、その場で外せるようにする。

## 9. 詳細設定（操作判断 18〜23）

- 右ペインの下に「詳細設定」を置き、開閉できる。開閉の状態は、パーツを選び直しても保つ。
- **位置・大きさ・回転**を数値で編集する。ドラッグでの編集は作らない。
- **「いつ使うか」**：いつも ／ 右腕が〇〇のとき ／ いまの向きとポーズのとき。それぞれ Character Schema の `transform` と `overrides.transform` に対応する。条件つきの補正を初めて作るときは、いまの値を写して始める。
- **中心（`pivot`）**：選択肢は「パーツの中心」「キャンバスの中心」「数値で指定」。既定は「パーツの中心」。
  - 「パーツの中心」は、**その Part について現在描画の対象になっている Layer 群の、透明でない画素の外接矩形の中心**である（設計書 §20.2）。画素を調べる処理は `src/web/` に置き、求めた座標を Character の `pivot` として保存する。
  - 「キャンバスの中心」は、`pivot` を書かないことで表す（Asset 仕様 §9 の既定値）。
  - 補正を初めて作るときに `pivot` を書く。すでに `pivot` を持つ補正の値を、ポーズの変更などで勝手に書き換えない。
- **内部情報**：Part ID、category、Instance ID を小さく表示する。
- **保存されている設定**：外しているパーツの Instance の一覧と、削除。
- 装備順の並べ替えは作らない。

## 10. 保存・読込・書き出し・注意（操作判断 24〜31）

- **保存**：Character JSON をダウンロードする。`requirements` は保存のたびに作り直す（`stringifyCharacter`）。
- **読込**：ファイルを選ぶ。INVALID なら開かずに理由を知らせ、いまのキャラクターはそのまま。UNRESOLVED は読み込む。
- **新規作成・読込の前**：保存していない変更があれば確認する。変更があるかどうかは、最後に保存・読込した時点の JSON との比較で求める（Character には入れない）。
- **PNG**：EXPORT の段でだけ出力する。1600×2400、透過、いまの状態 1 枚。
- **書き出せないとき**（Character Schema §10.2.1）：理由と、直すための操作を示す。描画される Layer が 0 枚 → 「向きを正面に戻す」など。実装が知らないポーズ → 直せないので、その旨だけ伝える。
- **状態の見せ方**：VALID のときは何も出さない。それ以外は、名前の横の印、プレビューの下、右ペインで知らせる。「UNRESOLVED」「INVALID」という語は利用者に見せない。
- **文の作り方**：core が返す状態とコード（`part-missing`、`pose-unknown`、`format-version-unsupported`、`canvas-mismatch` など）を、`messages.ts` で利用者向けの文にする。対応する文のないコードは、内部の文をそのまま出す（情報を隠さない）。検証器の細かい内容は「詳細」として開けるようにする。
- **設定**：詳細設定を常に開くかどうか、版の情報。

## 11. UI が持ってよい状態

`Phase1C1_Wireframes.md` §6 の表のとおり：いまの段、開いている大分類と小分類、編集対象、詳細設定の開閉、「いつ使うか」、保存していない変更の有無、最近使った色、表示中の通知。これらは保存しない。

これ以外で UI が状態を持つ必要が出た場合は、レポートに理由を書く。

## 12. 実装の進め方

1. 最小 UI を `src/minimal/` へ移し、既存のテストとスモークテストが通ることを確かめる（【確認 1】の決定による）。
2. `catalog.ts`・`labels.ts`・`messages.ts` と、`session.ts` の拡張（DOM 非依存の部分）を先に作り、テストする。
3. 画面の枠（ヘッダー、4 列、下の帯）と CUSTOMIZE の Part 選択を作る。
4. 色、表情、ポーズ・向き、詳細設定を順に足す。
5. CREATE と EXPORT、注意の表示、保存していない変更の確認を足す。
6. スモークテストと検証レポート。

各段階の完了ごとにコミットする。

画面を毎回すべて作り直す Phase 1-B の方式は、入力中の部品（色の選択、数値の入力、スクロール位置）が失われやすい。**更新する範囲を部品ごとに分ける**作りにしてよい。ただし、どの部品も Character と上の UI の状態から描けること（DOM にしかない状態を作らないこと）を守る。

## 13. テスト

既存の 298 件を壊さない。新たに最低限、次を自動テストする（DOM なし）。

- 分類の構成が、Asset 仕様の全 category を過不足なく含む
- 表示名の辞書に、標準の状態・Pose Definition・VIEW・共有色のキーがすべてある
- 新規作成：基本のパーツあり／なし、全体の色の初期値
- カードの選択：入れ替え、「なし」、なくせない分類、複数選べる分類の切り替え
- 外したパーツを選び直すと、設定と位置が戻る
- 一覧の各カードの状態（選択中・使える・使えない理由）
- 全体の色の編集、切り離し、戻す
- 表情のプリセットの適用と、「カスタム」の判定
- 向き：素材のない向きの判定、読み込んだ向きの保持
- `pivot`：「パーツの中心」の座標が、描画対象の Layer の外接矩形の中心になる。「キャンバスの中心」では `pivot` を書かない。既存の `pivot` を書き換えない
- 保存していない変更の判定
- 状態とコードから利用者向けの文への変換（内部の語が文に出ないこと）
- 書き出しの可否と、直すための操作

実際のブラウザでは、ヘッドレス Chrome のスモークテスト（`smoke:creator`）で次を通す。

> CREATE で名前を付けて始める → 髪と服を選ぶ → 色を変える → 「このパーツだけ色を変える」 → 表情のプリセット → 右腕をポケットにしてコートの注意が出る → 詳細設定で位置と回転を変える → 保存 → 新規作成（確認が出る）→ 読込 → EXPORT で PNG を保存 → 保存前と同じ画像

加えて、見つからない素材、知らないポーズ、読み込めないファイル、素材のない向きの各場合で、利用者向けの文が出て、内部の語（UNRESOLVED、Part ID など、定めた場所以外）が画面に出ないことを確かめる。

## 14. 今回やらないもの

設計書 §18 のとおり：VARIANT の本実装、PORTRAIT、複数画像・ZIP・一括出力、OUTFIT の継承、カスタム素材の導入、装備順の並べ替え、Undo / Redo、IndexedDB による自動保存、スマートフォン向けの配置、正式素材の制作。

加えて今回は作らない：ドラッグでの配置、検索・タグ・お気に入り、状態のサムネイル、ポーズのプリセット、色のパレットやスポイト、多言語の切り替え（辞書の形だけ用意する）。

「便利そうだから」という理由で足さない。足したくなったものは、実装せずレポートに書く。

## 17. 完了時の報告

1. 完了条件のうち、満たしたものと満たしていないもの。
2. 操作判断 1〜31 のうち、実装して使いにくかったもの、変えた方がよいと考えるもの。
3. 仕様（Asset Specification / Character Schema）への気づき。仕様書は書き換えない。
4. UI が持つことになった状態の一覧。
5. Phase 1-C-3 で人が操作して確かめるべき点。
6. **実際の Creator UI のスクリーンショット**（各段と、主な状態）。カードの大きさ、プレビューの大きさ、右ペインの詰まり具合などは、画像で判断する。

**1-C-2 が完了したら、そこで止めて結果を持ち帰る。** 1-C-2 は「設計した UI が実装できたか」、1-C-3 は「人が触って使いやすいか」で、確かめる対象が違う。
